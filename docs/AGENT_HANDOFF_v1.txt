This project uses imperative migrations. For a schema change:

  1. Read the current Supabase skill/docs/changelog first.
  2. Inspect the live schema with read-only SQL where needed:

       & $node $cli db query --linked "<read-only SQL>"

  3. Create the migration filename through the CLI; do not invent a timestamp:

       & $node $cli migration new <descriptive_name>

  4. Edit the created migration using apply_patch.
  5. Dry-run:

       & $node $cli db push --linked --dry-run

  6. Apply only after tests and review:

       & $node $cli db push --linked --yes

  7. Verify the live schema/data and migration list.
  8. Run the security advisor:

       & $node $cli db advisors --linked --type security --level error --fail-on error

Docker Desktop is not installed. Remote db push/query/advisors still work.
The CLI may warn that it cannot cache the migrations catalog because Docker is
absent; this warning does not mean the remote migration failed. Verify remotely.

Supabase security invariants:
  - Never expose SUPABASE_SECRET_KEY or service-role credentials in Vite.
  - Every public-schema table exposed through the Data API must have RLS.
  - Explicit GRANT and RLS are separate controls; verify both.
  - User collections, acquisition values, private notes, and direct messages
    are owner/participant scoped.
  - Store administrators do not receive a direct-message bypass.
  - SECURITY DEFINER RPCs must explicitly check auth.uid(), use an empty/fixed
    search_path, revoke PUBLIC/anon execute, and grant only the intended role.
  - Run the security advisor after functions, views, RLS, or grants change.

V7 live-feed fix:
  - trade_posts is in the supabase_realtime publication.
  - Existing member RLS remains the read boundary for every Realtime event.
  - The client subscribes only to joined community IDs.
  - Realtime changes trigger a quiet full feed reload.
  - Focus, visibility, and 15-second polling are fallbacks.
  - The status filter defaults to All posts, so completed/closed posts do not
    look as if they disappeared.
  - Channel cleanup is tested to prevent account-switch leaks.

Diagnosis evidence before V7:
  - Four real trade posts existed in Test Dresden Community.
  - They came from two active member accounts.
  - All four were marked completed.
  - RLS simulations showed each account could read all four posts, including
    posts created by the other account.
  - The missing UI behaviour was stale clients plus the default Open filter,
    not a failed write or cross-account RLS denial.

Current expected behaviour:
  When member A posts or changes status, member B's already-open community board
  refreshes through Realtime. If the WebSocket fails, member B refreshes within
  15 seconds or immediately on returning focus. All persisted statuses are
  visible by default.
